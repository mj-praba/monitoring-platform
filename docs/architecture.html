Architecture reference

How monitoring‑platform fits together

A full-stack system for monitoring Android devices in real time: a React dashboard, an Expo mobile app, and a small backend monorepo built around one deliberate split — live delivery to a dashboard never waits on a database write, and a database write never waits on live delivery. This page traces that mechanism end to end.

01 — Orientation

System map

Two clients (web dashboard, mobile app) talk to a four-process backend. Kafka sits between the WebSocket layer and its two independent consumers. Redis and ClickHouse are provisioned but idle; the desktop app doesn't connect to any of this at all.

02 — Identity

Auth & access scope

JWT access + refresh tokens identify who; a three-level scope hierarchy decides what they can touch. A role assignment made at a higher level automatically covers everything nested beneath it.

Two token scopes, never interchangeable. A user-scoped token (issued at login) is required on /ws/dashboard/*; a device-scoped token (issued at pairing claim) is required on /ws/device/*. Each socket rejects the other token type outright.

03 — Onboarding

Device pairing

A short-lived, location-scoped code links an unauthenticated phone to an authenticated dashboard session — the phone never sees the user's own credentials.

04 — The core mechanism

Live metrics pipeline

One Kafka topic, keyed by device id, feeds two consumer groups with opposite scaling semantics — one shards for durability, the other broadcasts for fan-out. This contrast is the reason the pipeline looks the way it does.

06 — Read this before extending it

Known trade-offs

By design, documented on purpose — not oversights waiting to be found.

CPU is a proxy, not a real percentage Android exposes no permission-free, root-free way to read true system CPU load. The mobile app measures JS-thread timer overshoot instead — a genuine measurement, but of thread contention, not CPU%.
Every websocket instance eats the full topic Dashboard fan-out has no per-device Kafka subscription, so every horizontally-scaled apps/websocket instance consumes 100% of the topic regardless of local viewer count — the same cost Redis pub/sub already had.
Redis and ClickHouse are wired but idle Both keep their docker-compose service, config, and package — ready if a future use case (caching, analytics) needs them — but neither is on the metrics pipeline today.
Scoped RBAC is an "initial impl" A global role/permission catalog (not per-tenant); route-convention scope resolution rather than a fully generic resolver; scope_id is application-validated, not a DB-level constraint.
